COBOL 文件化

把程式讀懂，也讓下一個人看得懂

用 pp4z 解讀程式，再整理成方便查閱的文件。

下次接手的人，會想問哪些問題？

知道程式「大概在做什麼」之後，還需要留下欄位、流程和注意事項。這個練習會用 pp4z 解讀 CKP02，再把說明整理成方便查閱的文件。

1. 用 Explain code 閱讀程式

  1. 開啟 output/z-lab/CKP02.cbl，選擇 Z Code。
  2. 點 Start Workflow，在工作區選單選擇本機教材資料夾的 Run Workflow in〈你開啟的教材資料夾名稱〉，並核對下方顯示的本機路徑。
  3. 在 Bob workflows 找到 Explain code，點右側的 Start。
  4. 依流程選取這個檔案及 Developer 視角，閱讀程式說明。

回覆談到轉換條件後，可以追問實際執行時會遇到的情況，例如同一份資料再跑一次。

加入檔案：output/z-lab/CKP02.cbl、specs/change-request.md

追問執行時的行為

再用 specs/change-request.md 的重跑案例，逐步推導連續執行兩次的結果。

接著看看另一個小範例 IDSHIFT。它把資料定義放在 Copybook，另外附有測試程式和 JCL。把相關檔案一起交給 Bob，就能比較兩種寫法。

把相關檔案一起看
請根據附上的檔案，比較 CKP02 和 IDSHIFT 的資料定義與讀寫方式。IDREC.cpy 在哪裡被使用？JCL 的 EXEC 實際執行哪支程式？請指出依據，再列出執行前還需要的設定。

3. 整理成接手文件

保持 Z Code，點 Start Workflow，先選擇本機教材工作區，再於 Bob workflows 找到 Generate program documentation，點右側的 Start。依流程選取 CKP02.cbl；若需要指定儲存位置，放在 output/z-lab/。

把產生的說明檔加入同一個對話，切換到 Plan，想想還有哪些內容需要補齊。

這裡也加入 change-request.md：程式說明回答「現在怎麼運作」，影響分析則回答「為了新需求，接下來要改什麼」。兩份資料一起看，才能區分既有功能與新增工作。

4. 回到程式，確認說明

寫完文件後，請 Bob 重新看原始碼，沿著條件成立與不成立的路徑各走一次。這樣比較容易發現摘要和詳細說明是否前後不同，也能看到條件之後還會做哪些事。

檢查文件中的例子
請重新閱讀原始碼，依 DOC-SPEC.md 核對剛才的程式文件。每個判斷條件成立和不成立時，都各走一次，看看接下來會執行哪些動作、何時讀下一筆、何時結束。

也請重新計算欄位位置，檢查摘要、表格和例子是否一致。若文件與程式不同，修正文件並指出依據，再執行檢查。

影響分析請另外對照 specs/change-request.md，確認沒有把既有功能寫成這次要新增的工作。
預期回應

條件分支與欄位的核對、文件修正說明，以及檢查結果。

對照文件時，可以先看哪些地方？
  • 資料內的 EOF 會略過這一筆的轉換，接著仍會讀下一筆；READ 的 AT END 才會設定迴圈使用的 EOF 旗標。
  • 記錄第 14–16 位，對應 R-NAME 的第 3–5 位。閱讀欄位位置時，先看看是從哪裡起算。
  • 程式宣告 VALUE SPACE；實際空白編碼與資料集屬性，需要搭配主機環境確認。
  • 範例 JCL 執行 TESTSHIFT。CKP02 的正式 JCL 尚未提供。

檢查程式會核對格式與數值；閱讀這些段落，可以再確認正文有沒有把不同概念混在一起。

重跑的例子，應該怎麼看？

使用需求文件中的 0000123456，並讓第 14–16 位不是 EOF。第一次轉換得到 00123456 加兩個空白，第二次得到 123456 加四個空白。第一次後仍以 00 開頭，所以不能只用一個例子就認定重跑結果都相同。

output 裡會有 program.md、impact-analysis.md 和 facts.json。前兩份方便閱讀，facts.json 則用來檢查欄位及例子是否一致。
