需求規劃

這項需求會影響哪些程式？

從一個批次需求開始，練習看程式、問問題，再整理計畫。

動手修改前，先確認影響範圍

假設你要替資料轉換程式新增預覽功能，動手前需要先弄清楚：要修改哪幾支程式、哪些行的邏輯，以及是否影響其他作業。我們從這項需求開始，請 Bob 理解現有程式、分析影響範圍，再整理實作計畫。預覽功能要呈現的是「預計轉換幾筆資料」，與「需要修改幾支程式」分開說明。

1. 先認識這支程式

先理解各支程式的角色，再跟著一筆資料看 CKP02 的處理與轉換規則。不必先讀懂所有 COBOL 語法；切換到 Ask，一次問一個問題，看完回答再追問。這一段先理解現況，不修改程式或提交作業。

A. 理解程式各自的角色

Ask 模式

加入檔案：z-lab

分清用途與相依關係
這是一個我完全陌生的專案，請幫我認識這個系統是做什麼的、這些程式各自負責什麼？主要業務功能與程式分組是什麼？請把看得到的用途與相依關係整理給我，指出程式依據；看不出有關聯的，就先分開說明。
預期回應

各程式的角色、有來源依據的相依關係與待確認事項。

看回答時留意：Bob 應依程式中的 COPY、CALL 或 I/O 敘述說明關係，不能因為檔案放在一起就認定互相呼叫。CKP02 的檔案轉換、CIS14 的 IMS 相關處理，以及 IDSHIFT 的記憶體記錄轉換應分開理解；合成範例不是合庫正式系統的一部分。無法確認的業務用途先留下問題。

B. 跟著一筆資料走過 CKP02

接著聚焦 CKP02。想知道「程式在做什麼」，可以先問資料從哪裡進來、經過哪些判斷，最後寫到哪裡。

試試 Enhance prompt：把想法說清楚

先用自己的話寫需求，或把下面這段貼進輸入框，暫時不要送出。

Ask 模式

加入檔案：z-lab/CKP02.cbl

先寫出想做的事
我剛接手 CKP02，想知道它如何處理資料。請幫我整理成方便接手的說明。
預期回應

先比較輸入框中改寫前後的提問，確認補充內容符合你的目的。

  1. 用 @ 加入 CKP02，將這段提問放進 Bob 輸入框。
  2. 點選輸入框旁的星光圖示 Enhance prompt，查看改寫後的提問。
  3. 比較它補了什麼：工作目的是否相同？是否要求根據程式回答？預期成果是否清楚？有沒有加入你沒提出的修改或環境假設？
  4. 保留符合目的的補充，調整不合適的內容。確認後送出，或改用下方的提問範例，擇一即可。

先不用追求很長的提問。能說清楚這一步想知道什麼、根據什麼回答，就有了繼續追問的起點。改寫後的答案仍要回到程式核對。

請 Bob 指出段落後，在編輯器的大綱點到相同位置，對照說明與程式。

Ask 模式

加入檔案：z-lab/CKP02.cbl

認識 CKP02
我剛接手 CKP02，想先了解它如何處理一筆資料。請根據這支程式，依讀取、判斷、修改及寫回的順序說明，並指出對應段落。遇到需要其他檔案或執行環境才能確認的地方，請另外列出。先不用修改程式。
預期回應

程式的用途、讀寫流程，以及可以一起閱讀的段落。

看完說明，如果還不容易想像資料怎麼變，可以接著請 Bob 舉例。

Ask 模式

加入檔案：z-lab/CKP02.cbl

看一筆資料怎麼變
可以用一筆資料帶我走過轉換過程嗎？請根據欄位宣告，整理修改前後的內容和保留的部分。表格中的位置請註明從哪裡起算，讓我能跟著程式核對。
預期回應

一筆資料的欄位表，搭配修改前後的例子。

看回答時留意：從 1000-OPEN-RTN 的 OPEN I-O 與首次 READ，到 2000-PROCESS-RTN 的判斷、REWRITE 與下一次 READ，最後到關檔。沒有進入轉換段落的記錄也會走到 REWRITE；不要把「內容沒變」當成「沒有回寫」。

C. 把程式條件說成可核對的規則

Ask 模式

加入檔案：z-lab/CKP02.cbl

用白話說明轉換規則
如果要向接手的同事說明 CKP02，你會怎麼用白話解釋哪些資料會轉換、怎麼轉、哪些不轉？也請指出程式段落，並把還需要向業務確認的意思列出來。
預期回應

白話轉換規則、對應段落，以及需要向業務確認的問題。

看回答時留意：前兩碼為 00 且第 14–16 位不是 EOF 才進行轉換；轉換是將原識別欄位第 3–10 位移到前面，再補兩個空白。資料裡的 EOF 與 READ AT END 是兩回事。註解提到公司統編，但這不代表程式有檢查統編有效性；完整業務定義仍需確認。

如果回答太抽象，可以接著問：「請用前後各十個字元舉例，並把空白標出來。」若 Bob 提到資料庫、API 或未提供的呼叫者，追問：「這個判斷是從哪個檔案看出來的？」

完成後，試著自己說明：CKP02 讀寫什麼、何時轉換、EOF 代表什麼，以及還有哪些業務問題待確認。後續程式文件單元會再用 Z Code 的 Explain code 工作流程深入解讀，並整理成交接文件。

2. 看看需求會影響哪些地方

這次以業務填寫的 Word 需求申請單開始。開啟教材的 requests/change-application.docx，閱讀目前的困擾與希望改善的方式；單內還有需要向申請人問清楚的地方。

下載 Word 需求申請單。教材另保留 requests/customer-email.eml 作為同一需求的信件範例，本步使用 Word 申請單即可。

將 requests/change-application.docx 加入 Bob 對話，切換到 Ask。若目前版本無法讀取 DOCX，請用 Word 開啟，將申請單內文複製到同一個對話，再送出下方問題。本步不需要 Puppeteer 或另裝 MCP；若 Bob 提議透過這些工具讀檔，請改用貼上內文的方式。

Ask 模式

加入檔案：requests/change-application.docx

先釐清業務想做什麼
這是業務提出的需求申請單。請先用白話整理他們遇到什麼問題、希望改善什麼，再列出開始評估前最需要問清楚的幾個問題。把申請單裡已經說明的事、你的推測和還要請對方確認的事分開，先不要替他們決定做法。
預期回應

業務期待、待確認問題，以及需要向申請人補問的資訊。

看看 Bob 是否問到「預計改幾筆」的計算方式、試跑後誰來確認、正式處理時資料是否可能已改變，以及重跑的期待。由你扮演需求提出者補充回答；尚無答案就標為待確認，先在明確標示的假設下評估，不把 Bob 的建議當成業務已同意。

接著切換到 Z Architecture，從輸入框的 / 清單選取 /impact-analysis，再接上下方問題送出。

Z Architecture 模式

加入檔案：z-lab/CKP02.cbl、requests/change-application.docx

找出變更影響
根據這份需求申請單與剛才釐清的內容，哪些程式、資料和批次作業可能受影響？請對照目前看得到的程式，說明修改位置與原因；尚未確認的需求和相依關係請分開列出，不要當成已定案。
預期回應

已確認的影響，以及需要補資料才能確認的關係。

如果流程要求連線 Z Understand，請選擇包含這支程式的專案。手邊只有本機檔案時，先分析看得到的內容，跨系統的關係留待補齊資料後確認。

3. 把需求整理成計畫

現在知道程式大致怎麼運作，就可以討論怎麼改。DOC-SPEC.md 約定文件的章節和檢查方式；提問時引用它，Bob 就有格式可以依循。

規劃新需求時，現有功能和建議做法容易混在一起。因此這次多補一句，請 Bob 分開說明，方便你判斷哪些已經存在、哪些還要做。

Plan 模式

加入檔案：requests/change-application.docx、DOC-SPEC.md

規劃預覽功能
我想在批次執行前，先知道會改到多少筆資料。請閱讀 requests/change-application.docx，對照現有程式分析影響，再依 DOC-SPEC.md 規劃架構文件和實作清單。

請分開說明現有行為、建議的做法，以及還需要確認的資訊。主機程式和本機範例各自分析，先討論計畫，不修改程式。
預期回應

需要分析的範圍、文件內容，以及還需要確認的資訊。

若 Bob 一次問了多個問題，請用「Q1：…、Q2：…」分別回答；設計方案另外選擇。請核對它記錄的答案，不讓未回答的事項變成已確認決策。

閱讀計畫時，想想兩件事：哪些建議有程式可以對照？哪些還需要業務或系統資料？有疑問的地方，直接在同一個對話追問。

4. 請 Bob 寫成文件

計畫確認後，在同一個對話切換到 Agent。前面已經說清楚的內容，這裡不用再重述一遍。

Agent 模式

加入檔案：requests/change-application.docx、DOC-SPEC.md

依計畫完成文件
請依剛才確認的計畫和 requests/change-application.docx，完成架構文件與實作清單，存到 output，格式依 DOC-SPEC.md。

描述現況時，重新核對引用的原始碼；計畫中的建議保留為提案，需要環境資料才能確認的事項另外列出。完成後執行文件檢查並說明結果。
預期回應

output 裡的架構文件和實作清單，附上檢查結果。

Agent 模式

加入檔案：DOC-SPEC.md、output/architecture.md、output/checklist.md、z-lab/CKP02.cbl、samples/cobol/IDSHIFT.cbl、samples/cobol/IDREC.cpy、samples/cobol/TESTSHIFT.cbl、samples/jcl/IDSHIFT.jcl、requests/change-application.docx

一起檢查計畫
請對照原始碼、需求申請單和實際對話，依 DOC-SPEC.md 核對架構文件與實作清單。每個「已確認」決策是否都有對應的回答？設計能否達成需求，還有哪些矛盾或缺口？

修正有證據可判斷的錯誤；回答有歧義的決策退回待確認，不替我選。請分開列出課程已知環境、業務待確認、設計提案，以及尚未取得的本次執行證據，說明哪些會影響後續實作。
預期回應

文件檢查結果，以及仍需要補齊的資訊。

出現待確認事項是正常的，但先核對它們屬於業務問題、設計選擇，還是尚未執行的測試。課程已提供來源編碼與測試配置，不需取得生產資料集才能繼續。第 03 單元會驗證原有 CKP02；本單元的新功能提案仍需完成決策與設計後，才能另行實作。

完成後可以看什麼？

開啟 output/architecture.md 和 output/checklist.md。前者說明現況、提案及影響，後者列出要做的工作、前置條件與完成標準。七個分析面向與詳細格式都在 DOC-SPEC.md。
