需求規劃

我想先知道，這次會改到多少筆？

從一個批次需求開始，練習看程式、問問題，再整理計畫。

執行批次前，你想先知道什麼？

假設你準備執行一支資料轉換程式，想先知道這次會改到多少筆，確認後再套用變更。我們就從這個需求開始，請 Bob 幫忙看現有程式、找出影響範圍，最後整理成計畫。

1. 先認識這支程式

剛接手程式時，不必先知道每個欄位和段落的意思。先把 CKP02 加入對話，問一個接手工作時會問的問題。

Ask 模式

加入檔案：bank-source/reading/CKP02.TXT

認識 CKP02
我剛接手 CKP02，還不熟悉這支程式。請幫我說明它處理什麼資料、什麼情況會修改資料，以及整個批次是怎麼跑的。也請指出對應的程式段落，方便我一起看。
預期回應

程式的用途、讀寫流程，以及可以一起閱讀的段落。

看完說明，如果還不容易想像資料怎麼變，可以接著請 Bob 舉例。

Ask 模式

加入檔案：bank-source/reading/CKP02.TXT

看一筆資料怎麼變
可以用一筆資料帶我走過轉換過程嗎？請把欄位位置、修改前後的內容，以及沒有被修改的部分整理成表格。
預期回應

一筆資料的欄位表，搭配修改前後的例子。

2. 看看需求會影響哪些地方

需求寫在 change-request.md。切換到 Z Architecture，從輸入框的 / 清單選取 /impact-analysis，再接上下方問題送出。

Z Architecture 模式

加入檔案：output/z-lab/CKP02.cbl、specs/change-request.md

找出變更影響
如果要加入 specs/change-request.md 的預覽功能，哪些程式、資料和批次作業可能受到影響？請幫我區分已經查到的關係，以及還需要補資料才能確認的部分。
預期回應

已確認的影響，以及需要補資料才能確認的關係。

如果流程要求連線 Z Understand，請選擇包含這支程式的專案。手邊只有本機檔案時，先分析看得到的內容，跨系統的關係留待補齊資料後確認。

3. 把需求整理成計畫

現在知道程式大致怎麼運作，就可以討論怎麼改。DOC-SPEC.md 約定文件的章節和檢查方式；提問時引用它，Bob 就有格式可以依循。

Plan 模式

加入檔案：specs/change-request.md、DOC-SPEC.md

規劃預覽功能
我想在批次執行前，先知道會改到多少筆資料。請閱讀 specs/change-request.md，分析這項需求會影響哪些程式與作業，再依 DOC-SPEC.md 規劃架構文件和實作清單。先討論計畫，不修改程式。
預期回應

需要分析的範圍、文件內容，以及還需要確認的資訊。

閱讀計畫時，想想兩件事：哪些建議有程式可以對照？哪些還需要業務或系統資料？有疑問的地方，直接在同一個對話追問。

4. 請 Bob 寫成文件

計畫確認後，在同一個對話切換到 Agent。前面已經說清楚的內容，這裡不用再重述一遍。

Agent 模式

加入檔案：specs/change-request.md、DOC-SPEC.md

依計畫完成文件
請依剛才的計畫和 specs/change-request.md，完成架構文件與實作清單，存到 output。文件格式與檢查方式請依 DOC-SPEC.md。
預期回應

output 裡的架構文件和實作清單，附上檢查結果。

Agent 模式

加入檔案：DOC-SPEC.md、output/architecture.md、output/checklist.md

一起檢查計畫
請重新打開文件引用的原始碼，依 DOC-SPEC.md 核對架構文件與實作清單。修正和程式不一致的說明，再執行檢查；還需要補資料的地方，請另外列出。
預期回應

文件檢查結果，以及仍需要補齊的資訊。

完成後可以看什麼？

開啟 output/architecture.md 和 output/checklist.md。前者說明現況、提案及影響，後者列出要做的工作、前置條件與完成標準。七個分析面向與詳細格式都在 DOC-SPEC.md。
