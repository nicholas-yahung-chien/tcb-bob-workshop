# Workshop workspace rules

Use Traditional Chinese for learning artifacts. Read `SOURCE-MAP.md` and the requested prompt before acting.
The supplied cobol-explain-zh-tw skill supports Explain code. Generate program documentation already produces Chinese prose in the verified course environment; use its generated document directly. The program-docs-zh-tw skill is optional troubleshooting for English prose, not a required course step or an automatically injected workflow skill. Preserve workflow-generated documents under docs/; only create localized copies under output/zh-TW/ when requested.
Use 支 for programs, 項 for jobs, 行 for source lines, and 筆 for data records or transactions. Explicitly distinguish program change scope from data conversion counts.
Do not read `reference/` unless the user explicitly selects the reference examples.
`z-lab/` contains the supplied bank source set and must remain unchanged; verify it using source-manifest.json. `samples/` is synthetic teaching material, not a production banking system. `customer-source/` is optional local-only material.
Do not read outside the workspace. Do not contact external services, send mail, deploy, or modify git history while performing a lab.
Write general exercise results inside `output/`. Host exercises may create personal configuration, generated .cbl/JCL, reviews and reports directly in `host-lab/`, and downloaded records under `host-lab/logs/`. This is a suggested destination, not a required input location: read the actual workspace folder attached by the user, including root-level JOB folders. For the optional RC 4 exercise, create the separate variant and reports under `host-lab/rc4/` according to RC4-LAB.md; preserve supplied sources and the baseline run.jcl. Preserve supplied `host-lab` Markdown instructions and `z-tests/` test programs, fixtures and JCL template. Do not modify supplied `z-lab/` sources. Save course-authored documents under `output/`, preserve workflow outputs under `docs/`, and save host reviews and reports under `host-lab/`.
Connection setup uses the supplied root zowe.config.json and zowe.schema.json. Learners replace only YOUR_USER_ID and enter passwords through Zowe. Do not generate, merge or redesign connection profiles as a course exercise; do not read or modify parent/global profiles or retrieve passwords. Begin Bob-led exercises with program analysis after connection setup.
Do not modify `z-tests/`, `z-lab/`, `tests/`, `scripts/`, `samples/`, `specs/`, `prompts/`, or `reference/` to make checks pass.
Separate source-proven facts, proposals, and missing evidence. Cite a real file and line or paragraph for each source claim.
Never infer an actual Java/API/SQL/JCL system from a proposed architecture. Do not claim a mainframe compile, IMS execution, SAST rescan or premium feature was tested without evidence.
Do not identify CKP02 as VSAM: its source alone does not establish that physical file organization. Refer to the declared fixed-length file and mark dataset properties unknown.
Prefer file editing tools when saving Markdown or Python; preserve literal content and backticks.
In Ask mode, explain without writing. In Plan mode, plan only. For lessons 00–02, use Agent for workspace checks and personal environment records, Z Code for single-program explanations and approved program/data-dictionary documents, and Z Architect for dependency analysis and approved architecture, impact and implementation-plan documents. In either Z mode, a discussion-only prompt must not write files; an approved documentation prompt may save only its named outputs. Z Architect must not modify program code. Lessons 00–02 do not modify supplied programs or submit host jobs. For later exercises, follow the mode and scope explicitly stated by that lesson.
For the lesson 04 IMS database exercise, follow host-lab/IMS-LAB.md and review the pre-provisioned personal TCBLAB.JCL(IMSRUN). It matches z-tests/ims-run.jcl; do not require learners to generate, download or upload a replacement. Save the review and report under host-lab/ims/. Create a personal JCL copy only when the learner requests a modification, and analyze that actual submitted version. Preserve z-tests/ims-run.jcl. Read z-tests/IMSCKP.cbl alongside the JCL. The same source is pre-provisioned as TCBLAB.COBOL(IMSCKP); CIMS reads that member, not inline COBOL. The inline DBD/PSB definitions and separate IMSCKP helper are a teaching model using job-private databases, not the customer's existing IMS schema. CKP02 still runs against a sequential file. Distinguish application DL/I diagnostics, IMS system messages and actual binary-log utility output. Never substitute samples/logs/ims-events.csv for real run evidence.
Use bytes for the 400-byte synthetic record. Python is a behavior model, not an IMS or COBOL runtime.
When blocked, name the missing prerequisite and use the documented fallback. Do not invent test results.

Learners use the IBM Bob chat panel in VSCode with Premium Package for Z (PPZ). Use the selected mode and attached file context. Ask for approval through the IDE permission dialog when required. For PPZ workflows, use the language-extension copies in z-lab/; keep supplied z-lab/ sources unchanged.
Write documents for learners: task, source evidence, findings and next actions. Report only observed test commands, timestamps and results.

For requirements exercises, use requests/change-application.docx as the primary business input. Do not invoke Puppeteer, browser automation, external conversion services, or install/create an MCP server to read request documents. If DOCX cannot be read with available local file capabilities, ask the learner to open it in Word and paste its text. Keep requests/customer-email.eml as an optional email example; do not parse it automatically.

For planning, follow DOC-SPEC.md decision tracing and environment classification. Never expand ambiguous user answers into multiple confirmed decisions. Keep course baseline execution separate from proposed changes and production deployment. Correct incomplete designs before claiming implementation readiness.
