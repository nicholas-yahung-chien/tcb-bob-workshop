動手修改前，先確認影響範圍

假設你要替資料轉換程式新增預覽功能，動手前需要先弄清楚：要修改哪幾支程式、哪些行的邏輯，以及是否影響其他作業。我們從這項需求開始，請 Bob 理解現有程式、分析影響範圍，再整理實作計畫。預覽功能要呈現的是「預計轉換幾筆資料」，與「需要修改幾支程式」分開說明。

1. 先認識這支程式

先理解各支程式的角色，再跟著一筆資料看 CKP02 的處理與轉換規則。不必先讀懂所有 COBOL 語法；切換到 Ask，一次問一個問題，看完回答再追問。這一段先理解現況，不修改程式或提交作業。

A. 理解程式各自的角色

{{z-roles|分清用途與相依關係|Ask}}

看回答時留意：Bob 應依程式中的 COPY、CALL 或 I/O 敘述說明關係，不能因為檔案放在一起就認定互相呼叫。CKP02 的檔案轉換、CIS14 的 IMS 相關處理與其他程式應分開理解；未選讀 samples 時，不要求分析其中的 IDSHIFT。無法確認的業務用途先留下問題。

B. 跟著一筆資料走過 CKP02

接著聚焦 CKP02。想知道「程式在做什麼」，可以先問資料從哪裡進來、經過哪些判斷，最後寫到哪裡。

試試 Enhance prompt：把想法說清楚

先用自己的話寫需求，或把下面這段貼進輸入框，暫時不要送出。

{{enhance-start|先寫出想做的事|Ask}}
  1. 用 @ 加入 CKP02，將這段提問放進 Bob 輸入框。
  2. 點選輸入框旁的星光圖示 Enhance prompt，查看改寫後的提問。
  3. 比較它補了什麼：工作目的是否相同？是否要求根據程式回答？預期成果是否清楚？有沒有加入你沒提出的修改或環境假設？
  4. 保留符合目的的補充，調整不合適的內容。確認後送出，或改用下方的提問範例，擇一即可。

先不用追求很長的提問。能說清楚這一步想知道什麼、根據什麼回答，就有了繼續追問的起點。改寫後的答案仍要回到程式核對。

請 Bob 指出段落後，在編輯器的大綱點到相同位置，對照說明與程式。

看完說明，如果還不容易想像資料怎麼變，可以接著請 Bob 舉例。

{{01-layout|看一筆資料怎麼變|Ask}}

看回答時留意：從 1000-OPEN-RTN 的 OPEN I-O 與首次 READ，到 2000-PROCESS-RTN 的判斷、REWRITE 與下一次 READ，最後到關檔。沒有進入轉換段落的記錄也會走到 REWRITE；不要把「內容沒變」當成「沒有回寫」。

C. 把程式條件說成可核對的規則

{{z-rules|用白話說明轉換規則|Ask}}

看回答時留意：前兩碼為 00 且第 14–16 位不是 EOF 才進行轉換；轉換是將原識別欄位第 3–10 位移到前面，再補兩個空白。資料裡的 EOF 與 READ AT END 是兩回事。註解提到公司統編，但這不代表程式有檢查統編有效性；完整業務定義仍需確認。

如果回答太抽象，可以接著問：「請用前後各十個字元舉例，並把空白標出來。」若 Bob 提到資料庫、API 或未提供的呼叫者，追問：「這個判斷是從哪個檔案看出來的？」

完成後，試著自己說明：CKP02 讀寫什麼、何時轉換、EOF 代表什麼，以及還有哪些業務問題待確認。後續程式文件單元會再用 Z Code 的 Explain code 工作流程深入解讀，並整理成交接文件。

將 requests/change-application.docx 加入 Bob 對話，切換到 Ask。若目前版本無法讀取 DOCX，請用 Word 開啟，將申請單內文複製到同一個對話，再送出下方問題。本步不需要 Puppeteer 或另裝 MCP；若 Bob 提議透過這些工具讀檔，請改用貼上內文的方式。

{{request-clarify|先釐清業務想做什麼|Ask}}

接著切換到 Z Architect，從輸入框的 / 清單選取 /impact-analysis，再接上下方問題送出。

{{z-impact|找出變更影響|Z Architect}}

如果流程要求連線 Z Understand，請選擇包含這支程式的專案。手邊只有本機檔案時，先分析看得到的內容，跨系統的關係留待補齊資料後確認。

3. 把需求整理成計畫

現在知道程式大致怎麼運作，就可以討論怎麼改。DOC-SPEC.md 約定文件的章節和檢查方式；提問時引用它，Bob 就有格式可以依循。

規劃新需求時，現有功能和建議做法容易混在一起。因此這次多補一句，請 Bob 分開說明，方便你判斷哪些已經存在、哪些還要做。

{{02-plan|規劃預覽功能|Plan}}

若 Bob 一次問了多個問題，請用「Q1：…、Q2：…」分別回答；設計方案另外選擇。請核對它記錄的答案，不讓未回答的事項變成已確認決策。

閱讀計畫時，想想兩件事：哪些建議有程式可以對照？哪些還需要業務或系統資料？有疑問的地方，直接在同一個對話追問。

計畫確認後，在同一個對話切換到 Agent。前面已經說清楚的內容，這裡不用再重述一遍。

出現待確認事項是正常的，但先核對它們屬於業務問題、設計選擇，還是尚未執行的測試。課程已提供來源編碼與測試配置，不需取得生產資料集才能繼續。第 03 單元會驗證原有 CKP02；本單元的新功能提案仍需完成決策與設計後，才能另行實作。
